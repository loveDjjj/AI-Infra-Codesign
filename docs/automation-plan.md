# 自动探索与评估方案

本文只描述**当前机制、已知缺口和下一批实施顺序**。逐轮实验事实在 `data/experiments.jsonl`，AI 决策在 `data/decisions.jsonl`，课程过程在 `data/iteration-log.md`；不要在此继续累加“实施进展第 N 节”。

## 当前闭环

```text
目标池 → 已实现变量采样 → 硬剪枝 → 隔离构建 → 产物去重
      → 单案功能 → 单案时序 → 同硬件 P1/D1 组合
      → 官方整案 → 审计 → 结构提案
      → 隔离源码修改 → 默认产物再生与回归 → 新源码批次
```

主控在 `src/codesign_lab/search/pipeline.py`，调度、目标、采样、AI 分析和结构提案各有独立模块。`scripts/pipeline.py` 是兼容入口。官方工具冻结；探索缓存不能替代最终整案。AI 输出必须通过 schema、变量域、预算和来源校验，模型对话不是事实库。

截至 2026-09-28，三个隔离源码变更连续通过官方审计，最高为 49,283.865188 分。第四源码批次搜索结束：117 个任务终结、33 个单案观测、没有值得送官方整案的新组合；无正在运行的第五批次。根目录 `best.yaml` 仍为 joint28。上述“最高已审计”和“根源码已晋升”是不同状态。

## 当前最值得修的链路缺口

| 优先级 | 缺口与证据 | 最小修改 | 完成条件 |
|---|---|---|---|
| P0 | 跨源码 epoch 重复评估相同 P1 产物；第四批次 25 个 P1 产物身份均在第三批次出现，P1 estimate 累计约 20,396 任务秒 | 使用由官方工具身份、硬件、ASM、种子和阶段组成的精确共享缓存；先做冲突与失效差分测试 | 两个 epoch 的相同产物只冷评一次；不同身份绝不串用 |
| P0 | 结构监督器默认最多处理 2 个提案，重复 QKV 提案和一次基础设施型回归失败耗尽额度；后到的 P1 W2 提案未处理 | 持久提案队列、明确结构语义去重、把可重试基础设施失败与有效尝试预算分开 | 已验证提案不因无效重复而丢失；崩溃后可恢复 |
| P1 | 参数池耗尽后主控终止，只有结构改动带来足够整案增益才自动产生新源码批次 | 同一源码下允许新一轮有限预算 campaign，基于最近证据生成新目标；无新变量时明确停机 | 至少两轮目标形成、测量和反馈在相同源码下完成 |
| P1 | profile 在批次尾部才运行，可能令大部分探索槽位空闲等待诊断 | 对当前最佳及有价值的异常候选提前排 profile，并按真实产物身份复用 | 后续 AI 在目标池耗尽前取得有效 profile |
| P1 | `accept_release()` 对 joint28 的基线假设固定 | 从当前已审计 release 及当前源码 epoch 读取可验证的 P1/D1 起点 | 不再重复测未改变的基线案例；不能跨源码误复用 |
| P2 | 记录和看板生成成本随完整账本增长；当前账本约 19 MiB、生成看板约 20 MiB | 报告只嵌入必要字段，按需读取详报；测量生成耗时后再改 | 看板保留阶段与证据入口，文件明显缩小，成绩不变 |

任务秒是并发任务耗时之和，**不能直接等同于批次墙钟节省**。第四批次实际墙钟约 30 分钟；缓存收益要用相同候选与相同资源的对照来量化。已审计完整成绩在同一硬件下没有可预测更优组合，因此第四批次没有官方整案任务，是入围条件的结果，不是官方槽位阻塞。

## 搜索策略与容量

固定源码时先分析参数是否真的改变目标 ASM；小空间枚举，大空间用 Random 基线与 TPE 对照。硬规则只剪确定非法、精确重复或有证明的界；历史超功耗、资源压力和模型预测只能调整优先级。失败、超功耗和主机超时要区别记账，不伪造性能数。P1/D1 在硬件哈希相同时独立搜索、组合；换硬件则两案重新核对。

当前更大的性能空间是 **P1 W1/W2 结构**：现有隔离 profile 的 W1、W2 算子跨度分别约 96,699 和 92,001 周期，P1 NoC busy 约 49.45%。这是优先实验依据，**不是**“NoC 导致等待”的因果证明。已枚举的预载和 attention 网格不应在每个 epoch 原样重跑。新增结构变换必须默认关闭、保持三份基线产物逐字节一致，功能种子、功耗与官方整案随后验收。

CPU/内存预算由调度器按运行时资源准入。56 总槽位、其中 2 个官方槽位是上次批次配置，不是固定最优值；扩并发需以有效观测/小时、峰值 RSS、I/O 等待与正式验收排队时间验证。官方候选只要合格且超过当前已审计分数即可本地整案，不以网站的 +1000 分门槛限制本地测量。

## AI 与源码版本边界

使用一条全局分析会话理解跨 P1、D1、硬件的证据；各次调用的原始轨迹统一在 `data/agent-trace/`。分析快照只汇总真实观测、失败原因、活跃目标、预算和证据路径。模型可只读查看项目文件，输出结构化目标和实现提案，但不能把它的文字当成评分或绕过校验。实现提案在隔离源码内执行；旧 campaign 源码冻结。晋升只发生在严格审计、已保全原件和明确门槛之后；网站上传始终独立关闭。

当前最高分的三次 `epoch_verified` 属于嵌套隔离源码，不应在根目录将其标为 `promoted_record`。整理源码 epoch 的发布路径时，先保证已有隔离版本的哈希、报告和默认三产物可逐字节再生，再考虑收拢嵌套目录；直接移动运行中的源码或删 `workspace/implementation-loop` 会破坏复现。

## 验收方式

1. 回归：`PYTHONPATH=src .venv/bin/python -m unittest discover -s tests`。
2. 官方冻结：`verify_official()` 与原始报告 provenance 匹配。
3. 基线：根源码对 joint28 的硬件及 P1/D1 ASM 逐字节再生；结构变更另验证对应 epoch 的默认输出。
4. 搜索：同一候选仅一次冷任务、失败类型明确、恢复不重复记账；各算法在同预算和同初始证据下比较。
5. 发布：打包、ZIP 路径/CRC/解压大小及 `lab verify` 通过；Git push 与课程网站上传分开。

下一步先实现共享精确缓存和持久结构提案队列，再跑同源码连续两轮的完整闭环。MILP 仅在具体预算选择或资源分配子问题形成明确整数模型、且求解成本有实测收益后接入；超时的 `UNKNOWN` 不能写成已证明不可行。
