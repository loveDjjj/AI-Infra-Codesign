# 自动优化框架：证据驱动的多实现族流水线

本文件描述**现状、已落地修复、目标结构和验收顺序**。实验数值以 `data/experiments.jsonl` 与原始报告为准，AI 决策以 `data/decisions.jsonl` 为准，课程过程写入 `data/iteration-log.md`。本文不再累加逐日实施流水账。此版吸收了根目录《自动优化效率审计与改造方案 v3》的设计判断，并以本机代码和隔离批次为准复核。

## 1. 当前状态和核心问题

截至 2026-09-28，最高已审计整案是隔离源码 `official-1790581630771528243`，49,283.865188 分；根目录 `best.yaml` 仍是 joint28，47,957.06 分。第四源码批次已结束：117 个任务终结、33 个单案观测，没有预测更优的整案组合。第三、第四批次的 25 个 P1 产物身份相同，第四批次 P1 estimate 合计约 20,396 **任务秒**；批次墙钟约 30 分钟，二者不可混算。

现有程序已经具备独立 worker、内存准入、阶段依赖、精确缓存计算前锁、动态目标、TPE、异步分析、官方整案和审计。瓶颈在**不同源码版本串行接力、旧参数空间重测、有效缓存证据未被学习**。继续增大 worker 或提高模型调用频率不能解决这些组织问题。

当前结构链仍是「一个提案编码 → 默认再生 → 回归 → 功能 → 时序 → 官方整案 → 达到全局增益门槛 → 等旧批次释放锁 → 新源码批次」。这是一条串行爬山路径。目标改为：**少量冻结实现族并行推进，共用一个资源调度器；程序持续搜索已注册空间，AI 在关键证据和研究供给不足时规划。**

## 2. 不可改变的事实边界

- `vendor/official/` 冻结；最终正确性、周期、功耗、资格和分数只由未修改的官方通道确定。探索缓存不用于完整 grade。
- `data/experiments.jsonl` 保存实验事实；模型输出只作为经校验的研究提案。功能失败、超功耗、超时/OOM、缓存复用各有不同语义。
- 源码批次注册后冻结。结构修改先证明默认硬件和 P1/D1 ASM 逐字节一致，再验证新开关、功能、时序、功耗和官方整案。
- **研究准入**与**发布晋升**分离。新机制首个正确的单案结果即使未赢全局最佳，仍可获得很小的有界参数预算；晋升仍要求官方整案合格、来源可再生并审计。
- GitHub 提交、课程 ZIP、本地官方 grade 和网站上传彼此独立；网站上传仍使用显式脚本及其分数/时间门槛。

已有 `ResultCache` 在**计算前**持有跨进程锁，因此“缺少缓存 single-flight”并非现状。下一步要解决的是**调度前**发现相同任务并共享一个在途结果，避免等待同一文件锁的多个进程各占一个槽位。缓存键继续绑定官方评估器语义、硬件、case、ASM、阶段与功能输入/seed；最终官方 grade 不读取缓存。计费需分开记录「新冷调用」「当前 study 首次学到的有效事实」「重复 receipt」。

## 4. 目标结构：一个主控、多个冻结实现族

```text
全局 Planner（长期只读研究会话，按关键事件调用）
            ↓ 结构化提案和证据 ID
持久提案池 → 最多两个独立 Coder 会话 → 平铺的隔离源码 family
                                         ↓ 能力清单与来源核对
                 一个全局 task broker / 资源调度器
      build、回归、functional、estimate、profile、official、audit
                                         ↓
                  共享精确缓存 + 单一事实账本
                                         ↓
             同硬件、同工作负载/ABI 的 P1/D1 组合
```

初版只容纳 **2–3 个活跃新 family + 1 个已验证参照**；这是实现上限，不是实测最优并发。不能为每个 family 各开一套 56 槽位流水线。Planner 与 Coder 分开会话和锁；一个 coder 只能修改自己的隔离目录。Planner 正在分析时，已定义搜索空间继续由程序提出候选、功能筛选和单案评估。

**研究门槛**：来源固定、修改范围合法、默认输出复现、目标产物确实改变、功能通过，并有可检验机制。首次单案慢于全局最佳不自动淘汰；只给有边界的小预算。**发布门槛**：同硬件真实组合、官方完整资格与审计，且达到明确晋升要求。异源码组合还必须完成各自生成器的复现审计与可打包来源证明；目前这一步尚未落地，因此只保留已验证的组合候选。无新合法工作或预算耗尽时正常停止，不以重复实验填满 CPU。

### 实现族版本包

每个 family 至少保存：`family_id`、冻结源码/生成器哈希、父版本、硬件/工作负载/ABI 身份、可取回的源码锚点、P1/D1 生成器入口、能力清单、原始报告引用。能力清单只声明**代码实际支持且产物生效**的变量、合法域、受影响算子、布局约束和建议代表点。编码 Agent 提交能力草案，程序通过构建和功能验证后登记；它不能直接改主控的全局变量白名单。

最高 `epoch_verified` 版本已有受保护的 `data/releases/official-1790581630771528243/generator-source.tar.gz`；本轮从归档隔离重建，硬件及两份 ASM 与 release 原件逐字节一致。平铺的恢复目录已生成 `workspace/family.json`，记录 release、生成器、控制代码和产物身份。该文件是可再生的运行清单，**不是**另一份长期事实账本；发布入口和异地备份仍待完善。不能说完整最高分源码只存在于嵌套 `workspace`，也不能说 GitHub 克隆已包含它。根目录 `best.yaml` 不因最高分不同源码而暗中改写。未来目标应显式绑定 `base_bundle_id`；旧 family 运行期间不随最佳指针漂移。

现在可执行 `./lab family-restore official-1790581630771528243 --out workspace/families/official-1790581630771528243` 重建并核对当前最高分源码。已有目录只有在当前控制代码、生成器文件、隔离最佳配置和三份构建产物都匹配时才复用。该命令只准备冻结源码锚点，不启动新搜索或网站上传。

### 跨版本组合

候选分案保留 `generator_ref + config_ref + hardware_hash + asm_sha256 + 证据`。P1 来自 family A、D1 来自 family B 时，不能只拼 YAML 后用第三份源码构建。两份 ASM 应由各自冻结生成器再生、核对相同硬件/ABI/工作负载，再进入完整官方 grade。同一案内两个结构修改不能按单独收益相加，须形成新的整合 family 验证。

## 5. 统一任务和预算

结构监督器当前会自行阻塞执行编码、回归、功能、时序与整案；直接把监督器开成多个进程会绕过全局资源预算。改造时将每一阶段变为持久 `task_id + attempt_id + family_id + execution_root + 依赖 + 资源估计 + 超时 + 结果身份`。`ImplementationLoop.process()` 每次只推进一个就绪阶段，提交到唯一 broker 后返回；完成事件再释放下游阶段。沿用现有 worker、启动意图、lease 和恢复检查，不再递归启动完整 pipeline。

提案池按明确的 `transformation_id + 父 family + 受影响算子 + 约束背景` 去重；文本相似只能提示人工或 Planner 核对，不能凭相似度硬删。分别计量不同研究假设、编码尝试、验证尝试与真实 CPU/RAM/墙钟。基础设施失败可有限重试，不吃掉“新假设”名额，但成本照记。一个非终态提案不能挡住其他可运行提案。

调度器在占资源前先查询结果索引与在途任务；同一精确评估键的订阅者共享一个冷计算。功能身份包含 seed；时序数值身份不因所要求的功能种子集合改变，但时序放行仍须逐个核对本次种子的功能证据。官方槽位始终独立预留。计算结果、恢复 receipt 和冷调用预算必须幂等。

## 6. AI 何时介入

程序自动执行已注册空间中的枚举/Random/TPE、硬剪枝、构建后产物去重、功能放行、同硬件组合和缓存反馈。TPE 的 `constant_liar=True` 已启用，不能再把“打开并行 TPE”当新改造。

Planner 只在三类情况分析：

1. 新结构首个可靠时序、关键 profile、功耗异常或明确反例提供了**机制证据**；
2. 有限对照表明当前假设失败或变量域已覆盖，需要**调整方向**；
3. 估计就绪任务可支撑的时间低于「规划 + 编码 + 构建」的实测补给延迟，且仍有合法方向和预算，才提前**补充研究供给**。

固定 batch/low-watermark 可作为保底，但不应因每八个重复缓存点调用模型。主控保留紧凑内存索引，仅在账本变动或必要的身份边界刷新；HTML 看板按脏标记和间隔生成。上述控制开销目前没有主机 profile 证明是最大瓶颈，先测再优化。

## 7. 优先研究的结构假设

**A：P1 W2 输入复用与 M/N/K 联合分片。** 当前 W2 有多个输出分片分别加载 K 分片输入；8 MiB 量级是按加载指令推导的**逻辑读取**，唯一输入约 0.5 MiB，不是实测 HBM 流量。先设计 2–3 个合法模板，连同 RF 权重/输入/累加器生命周期和部分归约一起核算，避免只调分片数字导致 RF 超容。

**B：W1–GELU–W2 有界流式计算。** 现有中间激活每层约 512 KiB，研究生产一个 M 块后立即供 W2 消费；比较省掉的材料化与新增权重重读、RF 占用和归约。首轮只做一两个生产者—消费者模板。

**C：功耗感知的局部依赖。** 直接移除 P1 W2 每行全局屏障的实验已使周期 397,212→398,172、峰值功耗约 19.16→21.70 W，不能再当作无风险方向。应逐项检查输入到达、RF 覆盖和 partial 归并的必要依赖，尝试局部事件、有限在途加载和错峰，对照周期、功耗与事件等待。

W1/W2 的现有算子跨度约 96,699/92,001 周期，支持优先检查，但跨度可能重叠；P1 NoC busy 约 49.45% 只提示资源压力，不证明因果等待。预载 K16 只减约 48 周期，旧网格降权而非永久禁用。硬件和数据流联合改变应在 A/B/C 有可靠差异后小范围展开。MILP/CP-SAT 只用于能明确建模的 RF 生命周期、映射或预算子问题，求解结果不是完整模拟器最优。

## 8. 分批交付与验收

| 批次 | 交付边界 | 必须看到的证据 |
|---|---|---|
| 1：确定性逻辑与证据 | 修触发器、TPE 缓存学习、整案账本裁剪 | DONE+ACTIVE 不误触发全池耗尽；同 study 缓存首次 COMPLETE/重复不加权；原始报告不变。本轮已落地并跑针对性回归 |
| 2：跨版本复用 | 全版本共享缓存、功能/时序键分离、登记并备份最高版本现有源码归档 | 第三/第四批次相同 P1 产物只冷测一次；不同输入必 miss；同时报告任务秒与墙钟。本轮接通新 epoch 缓存路径，最高源码归档隔离再生通过，真实缓存对照待做 |
| 3：并行结构执行 | 已完成 Planner/Coder 会话分离与提案精确去重；仍需将 `process()` 改成非阻塞阶段任务并接入统一资源租约 | A 时序运行时 B 可编码，C 可构建；全局容量不超限，失败恢复不重复启动 |
| 4：多 family 搜索 | 已有平铺源码锚点、研究分支小预算续跑和分来源组合再生；仍需能力清单、统一 broker、混合组合审计与打包 | 一个主控内两个不同源码 family 完成两轮；AI 暂停不阻塞现有合法任务；无工作时明确终止 |
| 5：结构实验 | A/B/C 至少两个独立假设，各有一两个代表点及有限邻域 | 功能、周期、功耗、流量/等待证据可解释机制；不要求每个假设都增分 |
| 6：效率对照 | 固定候选集比较新旧调度，再同预算比较 Random/TPE | 官方结果相同；重复冷调用下降、结构首证据耗时缩短、供给空窗减少 |

看板后续展示有效新产物率、跨 epoch 重复冷调用率、当前 study 的真实证据利用率、提案到首证据耗时、等待原因、供给空窗、已审计分数/墙钟。满 CPU 不是目标；重复工作即使把 CPU 占满也不增加知识。

每批交付均运行 `PYTHONPATH=src .venv/bin/python -m unittest discover -s tests`、独立 Optuna 后端测试，以及相应的实际字节再生或模拟器差分验证。只有结构算法发生改变才重新运行昂贵官方整案。本轮文档与评估链路整理本身不产生新的芯片成绩，也不触发网站上传。
