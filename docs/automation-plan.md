# 自动优化框架：证据驱动的多实现族流水线

本文件描述**现状、已落地修复、目标结构和验收顺序**。实验数值以 `data/experiments.jsonl` 与原始报告为准，AI 决策以 `data/decisions.jsonl` 为准，课程过程写入 `data/iteration-log.md`。本文不再累加逐日实施流水账。此版吸收了根目录《自动优化效率审计与改造方案 v3》的设计判断，并以本机代码和隔离批次为准复核。

## 1. 当前状态和核心问题

截至 2026-09-28，最高已审计整案是跨源码组合 `pair-w2-throttle-highest-full-1790611520350037544`，49,420.082119 分，受保护原件可独立再生；根目录 `best.yaml` 仍是 joint28，47,957.06 分。第四源码批次已结束：117 个任务终结、33 个单案观测，没有预测更优的整案组合。第三、第四批次的 25 个 P1 产物身份相同，第四批次 P1 estimate 合计约 20,396 **任务秒**；批次墙钟约 30 分钟，二者不可混算。

现有程序已经具备独立 worker、内存准入、阶段依赖、精确缓存计算前锁、动态目标、TPE、异步分析、官方整案和审计。瓶颈在**不同源码版本串行接力、旧参数空间重测、有效缓存证据未被学习**。继续增大 worker 或提高模型调用频率不能解决这些组织问题。

旧结构链是「一个提案编码 → 默认再生 → 回归 → 功能 → 时序 → 官方整案 → 达到全局增益门槛 → 等旧批次释放锁 → 新源码批次」。现在，结构提案本身进入主调度队列；回归、功能与单案时序作为探索任务并行，达到整案门槛后才进入独立的正式验收任务。有足够剩余时间和单案预算时，正确且功耗合格的新结构直接以冻结源码来源向**同一批次**注入有限邻域目标，不再必须等旧批次结束。目标仍是：**少量冻结实现族并行推进，共用一个资源调度器；程序持续搜索已注册空间，AI 在关键证据和研究供给不足时规划。**

## 2. 不可改变的事实边界

- `vendor/official/` 冻结；最终正确性、周期、功耗、资格和分数只由未修改的官方通道确定。探索缓存不用于完整 grade。
- `data/experiments.jsonl` 保存实验事实；模型输出只作为经校验的研究提案。功能失败、超功耗、超时/OOM、缓存复用各有不同语义。
- 源码批次注册后冻结。结构修改先证明默认硬件和 P1/D1 ASM 逐字节一致，再验证新开关、功能、时序、功耗和官方整案。
- **研究准入**与**发布晋升**分离。新机制首个正确的单案结果即使未赢全局最佳，仍可获得很小的有界参数预算；晋升仍要求官方整案合格、来源可再生并审计。
- GitHub 提交、课程 ZIP、本地官方 grade 和网站上传彼此独立；网站上传仍使用显式脚本及其分数/时间门槛。

## 4. 目标结构：一个主控、多个冻结实现族

```text
全局 Planner（长期只读研究会话，按关键事件调用）
            ↓ 结构化提案和证据 ID
持久提案池 → 最多两个独立 Coder 会话 → 平铺的隔离源码 family
                                         ↓ 能力清单与来源核对
                 一个全局 task broker / 资源调度器
      build、回归、functional、estimate、profile、official、audit
                                         ↓
                  共享精确缓存 + 单一事实账本
                                         ↓
             同硬件、同工作负载/ABI 的 P1/D1 组合
```

初版只容纳 **2–3 个活跃新 family + 1 个已验证参照**；这是实现上限，不是实测最优并发。不能为每个 family 各开一套 56 槽位流水线。Planner 与 Coder 分开会话和锁；一个 coder 只能修改自己的隔离目录。Planner 正在分析时，已定义搜索空间继续由程序提出候选、功能筛选和单案评估。

**研究门槛**：来源固定、修改范围合法、默认输出复现、目标产物确实改变、功能通过，并有可检验机制。首次单案慢于全局最佳不自动淘汰；只给有边界的小预算。**发布门槛**：同硬件真实组合、官方完整资格与审计，且达到明确晋升要求。异源码组合需各自冻结生成器逐字节再生；审计后保留两份源码快照，并由 ZIP 独立再生。无新合法工作或预算耗尽时正常停止，不以重复实验填满 CPU。

### 实现族版本包

每个 family 至少保存：`family_id`、冻结源码/生成器哈希、父版本、硬件/工作负载/ABI 身份、可取回的源码锚点、P1/D1 生成器入口、能力清单、原始报告引用。能力清单只声明**代码实际支持且产物生效**的变量、合法域、受影响算子、布局约束和建议代表点。编码 Agent 提交能力草案，程序通过构建和功能验证后登记；它不能直接改主控的全局变量白名单。

最高 `epoch_verified` 版本已有受保护的 `data/releases/official-1790581630771528243/generator-source.tar.gz`；本轮从归档隔离重建，硬件及两份 ASM 与 release 原件逐字节一致。平铺的恢复目录已生成 `workspace/family.json`，记录 release、生成器、控制代码和产物身份。该文件是可再生的运行清单，**不是**另一份长期事实账本；发布入口和异地备份仍待完善。不能说完整最高分源码只存在于嵌套 `workspace`，也不能说 GitHub 克隆已包含它。根目录 `best.yaml` 不因最高分不同源码而暗中改写。未来目标应显式绑定 `base_bundle_id`；旧 family 运行期间不随最佳指针漂移。

现在可执行 `./lab family-restore official-1790581630771528243 --out workspace/families/official-1790581630771528243` 重建并核对当前最高分源码。已有目录只有在当前控制代码、生成器文件、隔离最佳配置和三份构建产物都匹配时才复用。该命令只准备冻结源码锚点，不启动新搜索或网站上传。

### 跨版本组合

候选分案保留 `generator_ref + config_ref + hardware_hash + asm_sha256 + 证据`。P1 来自 family A、D1 来自 family B 时，不能只拼 YAML 后用第三份源码构建。两份 ASM 应由各自冻结生成器再生、核对相同硬件/ABI/工作负载，再进入完整官方 grade。同一案内两个结构修改不能按单独收益相加，须形成新的整合 family 验证。

## 5. 统一任务和预算

结构提案已拆成持久的 `implementation_code`、`implementation_validate` 和 `implementation_official` 三类任务：编码与单案验证占探索槽，正式整案才占独立验收槽，统一限制总进程数和内存，并预留一个普通官方验收槽。监督器终止时同一进程组内的结构子进程一起收尾，失败入状态并反馈全局 AI；仅因预算未启动的提案单独标记，不冒充设计失败。编码已完成而默认再生或回归出现已知基础设施错误时，只自动重试一次确定性验证，不重放 Codex 编码。有足够时间、目标额度和单案调用余额时，新结构将原研究记录、源码摘要和受影响案例的有限目标直接注入原批次；源码变化会阻止后续构建。否则沿用新批次交接，旧批次释放锁后启动，锁被其他批次占用时由轻量交接进程等待。**尚未完成逐关调度**：单案验证内部仍串行执行默认再生、回归、功能和时序。下一步将这些关卡分别持久化为 `task_id + attempt_id + family_id + execution_root + 依赖 + 资源估计 + 超时 + 结果身份`，完成事件再推进依赖；保留已有 worker 启动意图、lease 和恢复检查。

提案池按明确的 `transformation_id + 父 family + 受影响算子 + 约束背景` 去重；文本相似只能提示人工或 Planner 核对，不能凭相似度硬删。分别计量不同研究假设、编码尝试、验证尝试与真实 CPU/RAM/墙钟。基础设施失败可有限重试，不吃掉“新假设”名额，但成本照记。一个非终态提案不能挡住其他可运行提案。

调度器在占资源前先查询结果索引与在途任务；同一精确评估键的订阅者共享一个冷计算。功能身份包含 seed；时序数值身份不因所要求的功能种子集合改变，但时序放行仍须逐个核对本次种子的功能证据。官方槽位始终独立预留。计算结果、恢复 receipt 和冷调用预算必须幂等。

当前 `--max-case-calls` 统计的是功能与单案时序两个阶段的冷调用预留；一个全新案例通常需要至少 2 次额度，缓存命中会释放相应预留。本轮端到端冒烟测试先用 1 次额度，只走完功能；改为 2 次额度后 D1 功能与时序均完成。这是预算配置边界，不应把前一次记录成算子性能失败。

## 6. AI 何时介入

程序自动执行已注册空间中的枚举/Random/TPE、硬剪枝、构建后产物去重、功能放行、同硬件组合和缓存反馈。TPE 的 `constant_liar=True` 已启用，不能再把“打开并行 TPE”当新改造。

**当前策略：每个新的独立评估结果都立即请求全局 Planner 分析。** 单案结果、结构提案终态和官方整案审计结果进入持久触发游标；同一时刻到达的结果合并为一份快照，同一个全局 Codex 会话串行处理，后到的结果待当前回合结束后再处理。已知缓存重复与基础设施错误不伪装成新的性能证据；原始报告和实验事实先由确定性程序入账，AI 的总结、证据引用、下一步目标写入 `data/decisions.jsonl`，AI 不直接改事实账本或课程轨迹。结果触发不受一般冷却时间阻挡，模型调用仍受批次预算约束；预算耗尽时结果继续入账，但不能声称已由 AI 归纳。全局会话 ID 在本机 `workspace/ai-sessions/global.json` 跨批次接续；每次被接受的 AI 决策都会更新该指针。

此外，以下三类情况即使没有新单案结果，也值得分析：

1. 新结构首个可靠时序、关键 profile、功耗异常或明确反例提供了**机制证据**；
2. 有限对照表明当前假设失败或变量域已覆盖，需要**调整方向**；
3. 估计就绪任务可支撑的时间低于「规划 + 编码 + 构建」的实测补给延迟，且仍有合法方向和预算，才提前**补充研究供给**。

固定 batch/low-watermark 继续作为保底，不因重复缓存点调用模型。`configs/pipeline.yaml` 已切换到新的全局会话批次目录，启用 AI，并将调用预算设为 64；并发结果会合并，64 是上限而非预定调用次数。初始目标池为空时，显式启动的流水线先请求一次全局分析，由 AI 给出有界研究目标；如果 AI 判断没有合法方向且目标池仍空，就按耗尽条件结束。`./lab pipeline configs/pipeline.yaml` 仍只输出计划，只有加 `--execute` 才运行。主控保留紧凑内存索引，仅在账本变动或必要的身份边界刷新；HTML 看板按脏标记和间隔生成。上述控制开销目前没有主机 profile 证明是最大瓶颈，先测再优化。

## 7. 优先研究的结构假设

**A：P1 W2 输入复用与 M/N/K 联合分片。** 当前 W2 有多个输出分片分别加载 K 分片输入；8 MiB 量级是按加载指令推导的**逻辑读取**，唯一输入约 0.5 MiB，不是实测 HBM 流量。先设计 2–3 个合法模板，连同 RF 权重/输入/累加器生命周期和部分归约一起核算，避免只调分片数字导致 RF 超容。

**B：W1–GELU–W2 有界流式计算。** 现有中间激活每层约 512 KiB，研究生产一个 M 块后立即供 W2 消费；比较省掉的材料化与新增权重重读、RF 占用和归约。首轮只做一两个生产者—消费者模板。

**C：功耗感知的局部依赖。** 直接移除 P1 W2 每行全局屏障的实验已使周期 397,212→398,172、峰值功耗约 19.16→21.70 W，不能再当作无风险方向。应逐项检查输入到达、RF 覆盖和 partial 归并的必要依赖，尝试局部事件、有限在途加载和错峰，对照周期、功耗与事件等待。

W1/W2 的现有算子跨度约 96,699/92,001 周期，支持优先检查，但跨度可能重叠；P1 NoC busy 约 49.45% 只提示资源压力，不证明因果等待。预载 K16 只减约 48 周期，旧网格降权而非永久禁用。硬件和数据流联合改变应在 A/B/C 有可靠差异后小范围展开。MILP/CP-SAT 只用于能明确建模的 RF 生命周期、映射或预算子问题，求解结果不是完整模拟器最优。

多个已冻结实现族共用调度器的入口示例：

```bash
PYTHONPATH=src .venv/bin/python scripts/pipeline.py \
  --family-config workspace/families/<family-a> workspace/families/<family-a>/configs/search.yaml \
  --family-config workspace/families/<family-b> workspace/families/<family-b>/configs/search.yaml \
  --out workspace/pipeline/multi-family --workers 56 --full-slots 2 --execute
```

两个 `--family-config` 分别固定源码和搜索配置身份；构建、功能、时序、跨来源组合及官方验收共用同一资源队列。动态目标若选择带 `source_root` 和源码摘要的 family 单案记录作为 `base_record`，校验器会固定对应源码并让后续枚举、随机或 TPE 候选进入同一队列；全局分析快照会列出可选的 `available_family_bases`。family TPE 当前不导入其他源码的历史先验，避免把旧产物误作同一生成器的训练证据。本轮实际 TPE 只运行 1 个 trial，选中了已有的分组 8，结果由精确缓存复用并成功反馈；这证明链路可用，尚不能证明 TPE 比随机搜索更有效。结构编码、单案验证与正式整案现在以整个提案为单位共享主调度队列；单案验证内部阶段尚未拆开。单案账本记录来源路径和源码摘要，正式组合还会校验配置与完整源码哈希。看板改为按间隔生成，运行结束再生成最终状态，避免启动时先花一轮重报告成本。

分析模型现在由 `configs/pipeline.yaml` 的 `ai.model` 和 `ai.reasoning_effort` 明确指定，本机默认使用 `gpt-6-astra`、`medium`；会话恢复时同样传入该设置，不依赖服务器全局 Codex 默认模型。结构编码会话仍由 `implementation.model` 和 `implementation.reasoning_effort` 单独控制。
